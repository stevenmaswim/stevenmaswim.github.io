    Order matching engine

    Python · threading · heapq · pytest · GitHub Actions · C++17 port in progress

    github.com/stevenmaswim/order-book

    The problem

    An exchange matches buy and sell orders by price, then by arrival time. The engine has to be fast, it has to stay fair when many traders send orders at once, and a cancel should not cost a scan of the whole book.

    What I built

    A price-time-priority matching engine that sustains about 380K orders per second. That figure is the median of 5 runs on 12,000 seeded orders, and the benchmark is committed in the repo so anyone can re-run it.

    Decisions

    O(1) cancel with lazy deletion

    Each side of the book is a heap of (price, seq, id). A cancel only flags the order and lowers the depth count. Stale entries are popped when they reach the top. The arrival counter seq breaks ties in FIFO order, so no custom comparator is needed.

    Atomic id assignment and insert

    Giving an order its id and putting it in the heap happen as one step. Otherwise two concurrent orders could get ids in one order and land in the book in the other, which breaks FIFO priority.

    Measure the lock before blaming it

    The engine serializes every operation behind one lock, and CPython's GIL serializes bytecode anyway, so threads cannot speed it up. I benchmarked 3 threads and a single thread side by side: the medians match (382,092 vs 382,246 orders/sec), so lock contention costs almost nothing. The threads are there to prove correctness under contention, not speed.

    Results

    • About 380K orders/sec (5-run median, 12,000 seeded orders, committed in-repo).
    • After every stress test, invariant checks assert that filled + remaining + cancelled = quantity, that the book is never crossed, and that trades happen at the maker's price.
    • 56 unit tests, run in CI.
